Normalization

Formal normalization: from one unnormalized form to BCNF across all database entities.

Dependencies and Candidate Keys
  • F1 & F11: sale_id → sale_date, status, sync_status, client_id, seller_id, buyer_account_id; {seller_id, client_id} → sale_id
  • F2 & F3/F4: seller_id → first_name, last_name, barangay_zone, slp_association; account_id ↔ username
  • F5 & F6: product_id → product_name, unit_of_measure, unit_price, seller_id, category_id; {product_name, seller_id} → product_id
  • F7 & F8: category_id ↔ category_name
  • F9 & F10: {sale_id, product_id} → quantity_sold, unit_price_at_sale; {quantity_sold, unit_price_at_sale} → line_total
  • Candidate Keys: Primary key is {sale_id, product_id}. Alternate keys: {sale_id, product_name}, {client_id, product_id}, {client_id, product_name, seller_id}.
  • Price Snapshot Note: unit_price_at_sale is an intended price snapshot tied to the sale line, ensuring historical integrity.
3 · Normalization
Decomposition Process

UNF (Unnormalized Form) ▸

SALE_FORM
(sale_id, sale_date, status, sync_status, client_id, seller_id, first_name, last_name, barangay_zone, slp_association, buyer_account_id, buyer_username, {product_id, product_name, unit_of_measure, unit_price, category_id, category_name, quantity_sold, unit_price_at_sale, line_total}) Anomalies: Non-atomic repeating product groups; insertion anomalies (cannot add unused categories); update anomalies (duplicated seller/product metadata); deletion anomalies.

1NF (First Normal Form) ▸

Flattens repeating product groups into individual atomic rows.
R1 Schema: (sale_id, sale_date, status, sync_status, client_id, seller_id, first_name, last_name, barangay_zone, slp_association, buyer_account_id, buyer_username, product_id, product_name, unit_of_measure, unit_price, category_id, category_name, quantity_sold, unit_price_at_sale, line_total) Primary Key: {sale_id, product_id}

2NF (Second Normal Form) ▸

Removes partial dependencies on part of the composite key {sale_id, product_id}:
  • • SALE_HEADER(sale_id, sale_date, status, sync_status, client_id, seller_id, first_name, last_name, barangay_zone, slp_association, buyer_account_id, buyer_username)
  • • PRODUCT_INFO(product_id, product_name, unit_of_measure, unit_price, seller_id, category_id, category_name)
  • • SALE_LINE(sale_id, product_id, quantity_sold, unit_price_at_sale, line_total)

3NF (Third Normal Form) ▸

Removes transitive dependencies (TD1: sale_id → seller_id, TD2: sale_id → buyer_account_id, TD3: product_id → category_id, TD4: line_total derivation):
  • • Sales(sale_id, sale_date, status, sync_status, client_id, seller_id, buyer_account_id)
  • • Sellers(seller_id, first_name, last_name, barangay_zone, slp_association)
  • • Accounts(account_id, username)
  • • Products(product_id, product_name, unit_of_measure, unit_price, seller_id, category_id)
  • • Categories(category_id, category_name)
  • • Sale_Details(sale_id, product_id, quantity_sold, unit_price_at_sale) [line_total kept as GENERATED STORED column]

BCNF (Boyce-Codd Normal Form) ▸

Verifies that every determinant across all 12 system tables is a candidate key / superkey.
Verified Tables: Accounts, Sellers, Categories, Products, Sales, Sale_Details, Inventory_Transactions, Expenses, Capital_Management, Capital_Ledger, Receipts, Contact_Messages. No determinant violations remain.

Proofs & Guarantees
  • Lossless-Join Proof (Heath's Theorem): Every binary split joins on a key of one of the decomposed tables:
    ▪ S1: SALE_HEADER ∩ SALE_LINE = {sale_id, seller_id} → SALE_HEADER
    ▪ S2: PRODUCT_INFO ∩ SALE_LINE = {product_id} → PRODUCT_INFO
    ▪ S3: Sellers ∩ Sales = {seller_id} → Sellers
    ▪ S4: Accounts ∩ Sales = {buyer_account_id} → Accounts
    ▪ S5: Categories ∩ Products = {category_id} → Categories
  • Dependency-Preserving Proof: Every functional dependency (F1 to F11) lies completely inside a single final relation. No inter-table joins are required to enforce functional dependencies.
  • Historical Price Preservation: unit_price_at_sale captures historical transaction state and depends on {sale_id, product_id}, maintaining complete auditability without normalization conflict.
